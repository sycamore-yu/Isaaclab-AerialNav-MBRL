# 分档稳定模型与退化恢复协议

本协议用于 2026-10-29 用户要求的下一轮 fresh 对照，取代旧版“最低 20% 才建立稳定参考、持续覆盖一个文件”的恢复规则。它只控制同阶段检查点和学习率，不改变任务损失、首次失败统计或 80% 课程晋级规则。实现见 [optimization.py](../../src/isaaclab_navrl/zhang/optimization.py)，边界测试见 [test_optimization_controls.py](../../tests/test_optimization_controls.py)。本文件说明实现协议，不代表新实验已经启动或验收。

## 稳定档：三份自然报告，而非单次最好成绩

默认档位为 **5%、10%、…、80%**。每收到一份新的、由自然结束回合组成的训练报告，控制器更新最近三份报告的窗口；只有三份报告的成功率跨度不超过 **5 个百分点**，才可以保存稳定档。

设窗口最小成功率为 `ref`。本次保存所有满足 `level <= ref`、且当前阶段尚未保存的档位。例如三份报告为 11%、12%、13%，可以同时登记 5% 和 10% 两档；两档保存的是同一训练时刻的状态，记录的实际参考均为 **11%**。后续稳定在 21%、22%、23% 时新增 15% 和 20% 档，原 5% 和 10% 档的文件与元数据保留。只在已经保存的档内继续改善，不会覆盖该档或偷偷改变它的参考值。

档位由十进制起点、步长和整数档索引生成，避免浮点累加把 15% 写成略高于 15% 的值而漏掉边界。可配置字段为 `stable_min_success=.05`、`stable_level_step=.05`、`stable_max_success=.80`、`stable_reports=3`、`stable_max_spread=.05`。

**阶段达到 80% 与稳定达到 80% 是两件事。** 当前课程仍按原自然报告的 80% 阈值晋级。若首次 80% 报告到来时没有三份合格的稳定报告，该阶段可以保存 `stage_checkpoint` 并晋级，但不能将它标成 `stable80`。本控制器不会为了补齐稳定报告延迟阶段晋级，也不会拿单份通过报告补造稳定历史。

## 先减学习率，再观察，最后决定恢复

退化参考来自**同阶段最高已保存档**的实际稳定窗口最小值。默认退化条件为严格不等式：

\[
\text{current} < \text{ref} - \min\bigl(0.05,\max(0.02,0.30\,\text{ref})\bigr).
\]

各数值是 0～1 的成功率；0.05 是 5 个百分点，不是参考值的 5%。恰好等于阈值不算退化。

| 实际参考 `ref` | 下降幅度 | 退化条件 |
| --- | --- | --- |
| 5% | 2 个百分点 | 当前成功率 < 3% |
| 10% | 3 个百分点 | 当前成功率 < 7% |
| 15% | 4.5 个百分点 | 当前成功率 < 10.5% |
| 20% | 5 个百分点 | 当前成功率 < 15% |
| 80% | 5 个百分点 | 当前成功率 < 75% |

1. 连续三份报告退化，先请求将学习率乘 0.5，保留最低学习率限制。遇到一份不退化报告，连续计数归零。
2. 降率执行成功后，再观察三份**新的**报告。只有这三份全部仍退化，才请求恢复当前阶段最高稳定档。中途有一份恢复到阈值及以上，则本轮不回滚。
3. 恢复后清空稳定报告窗口、退化和观察计数，保留已保存的各档历史。沿用三份报告冷却期，冷却期间不重复触发恢复。

对应默认字段为 `degrade_reports=3`、`degrade_abs_drop=.05`（上限）、`degrade_min_drop=.02`（下限）、`degrade_relative_drop=.30`、`observe_reports=3`、`cooldown_reports=3`、`lr_factor=.5`。这些参数仍可独立配置。

## Runner 交接与状态边界

`RecoveryController` 只提出动作。保存时，`RecoveryDecision.levels` 列出全部新档；runner 先完成这些检查点的原子写入，再调用：

```python
controller.acknowledge("save_stable", checkpoints={level: path, ...})
```

映射必须完整对应本次新档，任何缺失、额外档或空路径都会拒绝，且不会部分登记。一次跨档允许同一个新状态或新路径服务多档；新档不能重用任何旧档路径，以免覆盖历史。每档登记 `level`、`stage`、`update`、`reference_success`、`checkpoint`。当前 `stable_checkpoint` 始终指向最高已保存档。

恢复只加载当前阶段对应的学习状态：策略、优化器和配套归一化，以及启用时的 critic/AHAC 状态。runner 保留当前较低学习率及持续上限，重置环境、GRU、动作和观测延迟缓冲、速度窗口。**全局更新数、真实环境样本数、耗时、训练报告、晋级事实、全局 RNG 和 critic 私有 RNG，以及累计 critic/AHAC 工作计数均不回滚。** 控制器自身和检查点档案也不从旧模型文件恢复。

阶段切换时清空活动控制器的档案与参考；runner 保留已写入各阶段目录的历史文件，禁止跨阶段选择恢复目标。控制器序列化版本升至 **2**，恢复普通控制器状态时要求版本、阶段、完整配置一致；旧版状态直接拒绝，不做语义不明的兼容转换。

## Plateau 的新默认

`make_plateau_scheduler` 的默认 `patience` 改为 **2**，其他默认不变，继续使用官方 `ReduceLROnPlateau(mode="max", threshold_mode="abs")`。按照该调度器的计数规则，一次最好报告建立基准后，连续三份无显著改善报告才发生降率；这与“每两份报告无条件减半”不同。`patience` 仍可显式配置用于对照。

Plateau 与恢复控制若在同一报告同时请求降率，runner 仍只降低一次。所有 patience 均计自然训练报告，不计 optimizer updates；批量环境数、AHAC 时域和报告间隔变化时，不应把相同 patience 直接解释成相同采样预算。

## 验证范围

局部用例覆盖 5% 下限、跨档保存、旧档不覆盖、实际 `ref`、严格阈值的下限/相对段/上限、三份连续退化、降率后的观察、最高档恢复、冷却、阶段隔离、JSON 往返和版本拒绝，以及 80% 晋级与稳定档分离。最初完成的19个纯 Python 控制器用例及语法检查，已由后续真实集成回归扩展，不能再概括为“仅语法检查”。

2026-10-29 主代理的集成执行回执如下；路径均相对于项目根目录，原日志保留各轮的真实结果：

| 回执 | 实际范围与结果 |
| --- | --- |
| `logs/restart_checks/initial_unit.log` / `initial_unit.xml` | 包含 `test_optimization_controls` 的初轮回归：159通过、16失败；16项失败均为随后修正的 ground 测试 fixture，不将此轮记为全部通过。 |
| `logs/restart_checks/controls_unit.log` / `controls_unit.xml` | 配置、runner、ground、critic state、actor-critic、DCOL 定向回归：111通过、73个子测试。runner 的稳定档不可覆盖、恢复同阶段最高档、Adam与目标高度身份检查均已在集成环境实际执行。 |
